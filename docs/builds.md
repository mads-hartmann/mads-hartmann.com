# Bazel builds with Nix tools

Nix owns runtime versions and package dependencies. Bazel owns the graph of site
inputs, generated artifacts, and tests. Devenv owns the interactive environment;
Makefiles own preview processes. GitHub Actions calls the same build/test commands and
continues to own deployment credentials, approvals, and ordering.

## Commands

From the repository root, inside `devenv shell`:

```sh
bazel build //:uses_manifest  # Uses content, routing and manifest only
bazel test //:uses_test      # Uses content, footer and routing checks
bazel build //:sites         # All deployable site artifacts
bazel test //...             # Site, cross-site, workflow and manifest checks
scripts/build.sh uses        # Also export Uses artifacts to .build for Terraform
make check                  # Bazel checks, build/export and Terraform checks
```

Without activating devenv, a machine with Nix can use:

```sh
nix --extra-experimental-features 'nix-command flakes' shell --impure \
  --file dev/bazel/tools.nix bazel python --command scripts/build.sh
```

Terraform 1.16.5 validation remains separate: its checks initialize
providers and run Terraform's own tests. Terraform plans, applies, invalidations,
and smoke tests are not cached Bazel actions.

## Dependency graph

`BUILD.bazel` declares separate content, routing, and manifest targets for
`homepage`, `blog`, `uses`, and `computer`. Content targets depend on their own sources,
their renderer, the shared footer, and the corresponding Nix tools. A blog edit
does not invalidate Uses. A shared footer edit invalidates all four builds.
The routing targets share `routing/redirects.json`; a change there can rerun all
four routing actions, but unchanged generated bytes retain their identity.

Each manifest depends on site content, its generated routing function, its
Terraform root and the shared static-site module. Terraform changes regenerate
the manifest without rebuilding HTML. Cross-site redirect checks are a separate
test that depends on all sites; each site's individual test can run independently.

There is no Git revision or workspace stamping in build inputs. A new commit
alone does not change an action key or a content version. Generated files are
written under `bazel-bin`; `scripts/build.sh` exports only the requested site's
artifacts into `.build`, retaining the layout consumed by Terraform.

## Tool ownership

`devenv.yaml` pins nixpkgs and nixpkgs-ruby. Runtime selections in
`dev/shared/versions.nix` are shared with devenv. `dev/bazel/tools.nix` constructs
the tools; `rules_nixpkgs_core` imports them into Bazel as declared dependencies.
Small tool metadata files embed immutable Nix store paths for the runtimes, npm
packages and gem environment. Their bytes are explicit Bazel inputs. Changing a
path therefore changes the consuming actions' cache keys. The build runner links
the appropriate immutable npm trees into its temporary source directory; Jekyll
image generation and asset fingerprinting run inside the same action. Ambient Node/Ruby installations
and mutable local `node_modules` or gem directories are not build inputs.

Nix realizes dependencies before Bazel actions run. Actions execute in Bazel
sandboxes with access to the host's Nix store. Remote execution is disabled for
these rules; a remote cache can still share results between compatible hosts.
macOS and Linux generally have different tool identities and action cache keys.

The blog uses Nix's gem build configuration, including native-extension fixes
and a Nix-provided Dart Sass executable. Update `gemset.nix` by running `bundix`
in the blog directory after changing its lockfile. No Bazel rule installs gems
or npm packages during a site build.

## Deterministic manifests

Each `.build/manifests/<site>.json` contains:

| Field | Meaning |
| --- | --- |
| `content_digest` | Hash of sorted relative paths and file byte hashes in the rendered site |
| `routing_digest` | Hash of the generated CloudFront routing function |
| `infrastructure_digest` | Hash of the site's declared Terraform files/module |
| `bundle_digest` | Combined identity of those three components |

Filesystem timestamps, output directory paths, Git SHAs, and tool versions are
excluded from these identities. A renderer/tool change can rerun the build and
still produce the same content digest. File additions, deletions, renames, and
byte changes are included. Manifests sit outside content directories, so
Terraform does not upload them as site pages.

Jekyll's build time is derived from the latest explicit post publication date,
plus one second to avoid Jekyll treating that post's date as an unset default.
Files are staged with normalized mtimes and the build runs in UTC. This replaces
the former Git commit timestamp, including the generated feed's update time and
default dates for undated collection documents. Production builds have no
wall-clock dependency; publishing future-dated posts requires an explicit
publication policy rather than relying on a later CI run.

These manifests are build outputs, not deployment-success records. The current
deployment workflow retains its existing source-based selection and Terraform
no-change checks. Bazel/Nix build configuration changes conservatively select all
sites in that gate. A future S3
deployment record can compare the content/bundle digests and record
`deployed_from_commit` only after successful deployment and verification. Shared
infrastructure outputs, deployment code and environment-specific variables must
also be considered when deciding whether a full deployment can be skipped.
Matching content hashes alone do not establish that infrastructure has no drift.

## CI and verification

The local `setup-build` composite action installs Nix, realizes Bazel/Python from
the shared expressions, and restores Bazel's disk cache. The cache archive key
uses the workflow commit to save snapshots; Bazel validates each cached action
using its actual inputs. This does not add Git SHA to site build identities.
Nix dependencies are realized separately and are not included in that disk cache.

Run the invalidation regression checks inside the development environment:

```sh
python3 scripts/check-build-cache.py
```

They use a temporary copy and test unchanged builds, documentation-only changes,
blog-only changes, Computer-only changes, Uses changes with identical rendered output, visible Uses
changes, shared-footer changes, Terraform-only changes, and a Nix tool change.
The working checkout is not modified.
